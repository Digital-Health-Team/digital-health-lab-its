Order & Transaction Flow — 3D Printing Service

How a made-by-order print job travels from order creation, through admin pricing and raw-material consumption, to live production progress updates and completion. Derived directly from the Laravel Actions, DTOs, models, and the Livewire Order Center.

Reality check from the code. Today the lifecycle starts at the admin, not the customer. Orders are created inside the admin Order Center drawer (CreateBookingAction tags them "Pesanan manual via Admin") — the admin can even create the customer's account on the spot. The customer-facing "browse → book → pay" journey described in the project brief is not yet wired up; the React user dashboard is still a stub and no public booking route exists. The flow below documents what the backend actually does.

01End-to-end lifecycle

Each step names the actor, the Action that runs, and the rows it writes.

1

Order is createdAdmin · Order Center

An admin opens the Create Order drawer, picks (or creates) a customer and a service, and saves. Two rows are born inside one DB transaction: the parent ledger and the booking detail. Price is still unknown, so the invoice total is 0 and payment is unpaid.

OrderCenter\Index::saveCoreOrder() CreateBookingData CreateBookingAction
transactions → total_amount=0, payment_status=unpaid  ·  service_bookings → current_status=pending, agreed_price=null
2

Admin reviews & sets the priceAdmin

Admin opens the order's Manage drawer → Pricing & Materials tab. They enter the slicer output (filament weight in grams, print time in minutes) and the final agreed price. Saving writes the price onto both the booking and the parent transaction — the invoice is now "ready for the user to pay".

OrderCenter\Index::saveCalculation() SlicerCalculationData UpdateBookingCalculationAction
service_bookings → slicer_weight_grams, slicer_print_time_minutes, agreed_price  ·  transactions → total_amount = final price
3

Stock check & material consumptionAdmin

Before/while producing, the admin records which raw material the job consumes. The Action guards the stock: if current_stock < quantity it throws and the whole movement is rolled back. Otherwise it logs an out movement linked to the booking and decrements the master stock atomically. Only materials with stock > 0 are offered in the dropdown.

OrderCenter\Index::deductMaterial() MaterialMovementData RecordMaterialMovementAction
raw_material_movements → type=out, quantity, service_booking_id  ·  raw_materials → current_stock −= quantity
↻

Restock (parallel inventory loop)Admin · Raw Material

When filament runs low, an admin restocks from the Raw Material screen by uploading a purchase receipt. One atomic transaction creates a reimbursement record (financial audit trail), stores the proof as a polymorphic attachment, logs an in movement, and increments stock. This feeds the stock that step 3 later consumes.

RawMaterial\Index RestockMaterialData RestockMaterialAction
reimbursements (status=pending) → attachments (receipt) → raw_material_movements (type=in) → raw_materials current_stock += quantity
4

Production progress updatesAdmin · Timeline

On the Production Timeline tab the admin posts updates: a status label (slicing → printing → revising → finishing → completed), a 0–100% slider, notes, and optional photo attachments. Each post inserts a progress row and syncs the booking's current_status to that label. The first post on a pending/negotiating order flips it to in_progress.

OrderCenter\Index::addProgress() ProgressUpdateData AddProgressUpdateAction
service_progress_updates → status_label, percentage, notes, updated_by  ·  attachments (photos)  ·  service_bookings → current_status synced
5

Completion & revenueSystem · KPIs

When the last progress update is finishing/completed, the order is treated as fulfilled. The Order Center and Super Admin dashboards aggregate revenue: completed/finishing bookings count toward realized revenue (today / this month), while active statuses (in_progress, printing, slicing, revising, negotiating) form projected revenue. Realized revenue is only counted on transactions whose payment_status = paid.

OrderCenter\Index::render() SuperAdmin\Dashboard\Index
revenueToday / revenueThisMonth = Σ agreed_price where status ∈ {completed, finishing}  ·  total_revenue = Σ transactions.total_amount where payment_status=paid

02Booking status lifecycle

service_bookings.current_status — driven by progress updates and admin edits.

pending→ negotiating→ in_progress / slicing→ printing→ finishing→ completed
side branches: revising cancelled

Payment status lives on the parent transaction independently: unpaid → paid / failed expired  — note: no implemented step flips it to paid yet (see gaps).

03Data model touched by the flow

One transaction (ledger) → many bookings; each booking accrues progress updates and material movements.

transactions

Parent payment ledger — one per order group
  • id PK
  • user_id FK → users
  • total_amount int (Rp)
  • payment_status unpaid|paid|failed|expired
  • payment_proof nullable path
  • expired_at datetime?

service_bookings

The order detail / job sheet
  • id PK
  • transaction_id FK
  • user_id · service_id FK
  • product_reference_id FK?
  • brief_description text
  • slicer_weight_grams int?
  • slicer_print_time_minutes int?
  • agreed_price int?
  • current_status string

service_progress_updates

Production timeline entries
  • id PK
  • service_booking_id FK
  • status_label string
  • percentage 0–100
  • notes text?
  • updated_by FK → users
  • + attachments polymorphic

raw_materials

Inventory master (stock balance)
  • id PK
  • brand · color · category FK
  • current_stock int
  • unit g / pcs …

raw_material_movements

Stock ledger (in / out)
  • id PK
  • raw_material_id FK
  • service_booking_id FK? (out)
  • reimbursement_id FK? (in)
  • type in | out
  • quantity int
  • created_by FK → users

reimbursements + attachments

Restock audit trail & files
  • reimbursements.id PK
  • title · total_amount · status
  • attachments.attachable_* polymorphic
  • attachments.file_url storage path
